Read-only root filesystems, dropped capabilities, bounded logs, health checks and a five-minute SIGTERM grace period are configured. The [deployment guide](DEPLOYMENT.md) covers Linux/NAS ownership, private Tailscale HTTPS, paired upgrades and backup/restore. ## Notes from W0 to W2
- **Free-voice make-ready time is a hard-coded assumption** (`ASSUMED_MAKE_RATE` in `src/lib/bookAudio.ts`: 0.9 s of audio per second, from one live Breeze run on the reference machine, 10.2 s of audio in 10.8 s). It should not stay hard-coded: the server could report its own measured generation rate from past jobs (or run a speed test) and the sheet would use that, saying "About" until a job has measured it. Not built; recorded as a known limitation on both sides. Because the rate is near real time, a long book takes about as long as it lasts, and the sheet says so (spec 10.1: "or the UI says how long it will take").
- **Voice order:** Gemini voices are listed alphabetically by the server. The `VoicePremium` board's Kore, Puck, Charon order is a curated sample; the board fixture is not changed and the live list is alphabetical. Accepted.
- **Breeze has no authentication**, so the client has no Breeze key field. The server's API still accepts a key if one is ever needed.
- **Chapter row word:** the current chapter keeps the board's "34%" look when Ready or On this device (the audio word stays available to screen readers); otherwise the audio word shows.

## Notes from W5
- **Status:** W0 to W5 built: 66 of 75 boards checked (0.00% to 0.53%; 9 left are 5 for W6 and 4 reference boards); 106 end-to-end flows against a real server; 736 unit tests.
- **One event stream per page.** The library, book page, player and offline engine each held their own stream; a browser allows about six connections per host over HTTP/1.1, so ordinary requests queued behind them and pages stopped updating. They now share one stream per listener (`subscribeSharedEvents` in `src/lib/sse.ts`); `e2e/streams.spec.ts` fails on the old behaviour (4 open at once) and passes now (1).
- **Offline.** IndexedDB holds the index, text, timings and audio (as ~1 MiB parts, committed atomically, so a chapter is On this device only when everything is durable and verified); downloads resume by Range, verify a SHA-256 (a pure-JS implementation, because `crypto.subtle` does not exist on plain http), and never replace a held chapter without the listener's choice. Removing a download never touches the server. The player prefers a held chapter online or off, opens a held book from local data when the server cannot be reached, and says why when a chapter is not on the device (O5).
- **Service worker and https.** Browsers only allow a service worker on https or localhost. On a plain `http://` LAN address the app shell does NOT load offline (held audio, text and timings still work once the app is open). Serve Bardic over https (for example Tailscale's certificate feature) for the full offline app; it also makes the app installable, which helps against Safari evicting storage for sites that are not installed.
- **Wi-Fi only** starts on only where the browser can tell Wi-Fi from mobile data (`navigator.connection.type`, Android Chrome). Elsewhere it would wait forever, so it starts off and the sheet says why.
- **Limits when away from home:** the device cannot know the server's chapter words (Ready, Making), the audiobook tier, or front/back matter, so a held book's page shows what the device knows; offline progress weights story chapters equally until the server is back; the listener's place-conflict and continue settings are not stored locally (defaults ask and continue, re-read on reconnect).
- **Not verified:** Safari and iOS (IndexedDB blobs, eviction, no `connection.type`), and a real socket reset during a download (tests truncate the body).
- **Copy:** UpdateAudio and ServerOffline boards say "Your computer"; UI-GUIDE says "Your Bardic computer". The screens follow the boards, so the wrap lines match.
